# site/ — what gets deployed

```
site/
  index.html          the whole page, regenerated by ../gen_tent_finder.py
  api/checkin.js      the check-in endpoint (Vercel serverless function)
```

Never edit `index.html` by hand — it is generated. Edit the sources one level up
and run `python3 gen_tent_finder.py`.

## Deploy to Vercel

1. Push the repository to GitHub, then **Add New → Project** in Vercel and import
   it. Or `npx vercel` from this folder.
2. **Root Directory: `app/site`.** That is what makes Vercel find `api/`.
   Framework preset: Other. No build command, no install step.
3. **Storage → Upstash for Redis → Connect** to the project. That injects
   `KV_REST_API_URL` and `KV_REST_API_TOKEN` on its own; the function reads
   either those names or the `UPSTASH_REDIS_REST_*` pair.
4. Redeploy once so the function picks the variables up.

Check it works:

```bash
curl https://<your-project>.vercel.app/api/checkin
```

`{"tents":{}}` means the store is connected. A 503 means step 3 is missing or the
project has not been redeployed since.

## Check-in

A guest who looks themselves up gets a **Jetzt einchecken / Check in now** button.
Pressing it writes `C9:309` into Redis. Flo's overview turns that tent green and
counts it.

**Without the endpoint the button simply does not appear.** The page probes
`api/checkin` on load and, if it gets nothing, renders no check-in UI at all — so
the same `index.html` still works opened straight from disk, on GitHub Pages, or
as the Claude artifact. It just does less there.

The check-in state lives only in Redis, keyed by campsite and tent number. No
addresses, no names, no device identifiers.

**What it does not do:** the endpoint accepts any well-formed tent id from
anyone who can open the page. Tent numbers are in the page, so a guest could
check in a tent that is not theirs. Nothing is destroyed by that — Flo can see
the arrival is wrong and it is one Redis field to clear — but if it matters, say
so and I will tie each check-in to the address hash instead.
